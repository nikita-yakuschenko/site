# Рабочее окружение на резервном сервере

Панель: https://development.avgst.ru. Сайт: https://avgst.ru. CMS: https://cms.avgst.ru.

В проекте `avgst`, окружении `production`, находятся три отдельные службы:
сайт, CMS и PostgreSQL CMS. Внутренняя база Dokploy к данным сайта отношения
не имеет. PostgreSQL приложения не публикует порт в Интернет.

CMS хранит медиа в `/var/lib/avgst/media`, сайт сохраняет кэш Next.js в
`/var/lib/avgst/site-cache`. Эти каталоги подключены через карточки Dokploy
и сохраняются при замене контейнеров. Секреты и параметры релизов хранятся
в `/etc/avgst` с доступом только root; их нельзя добавлять в Git.

Оба приложения собираются на GitHub-hosted runners и публикуются в GHCR.
Сайт использует `.github/workflows/site-image.yml`, CMS — существующий
`.github/workflows/cms-image.yml`. Push в `main` запускает соответствующий
workflow. `workflow_dispatch` позволяет повторить выпуск вручную.

На сервере работает runner `avgst-cms-reserve` с меткой `avgst-cms`.
У него нет доступа к Docker socket и секретам приложений; sudo разрешает
только установленные root скрипты `avgst-cms-release` и `avgst-site-release`.
Workflow не обновляет эти скрипты из checkout.

CMS перед обновлением делает копию PostgreSQL и применяет миграции.
Сайт проверяет source/revision образа, записывает digest в Dokploy и
проверяет запущенный контейнер вместе с `/api/health` и `/api/ready`.
При неуспешном выпуске сайта прежний digest возвращается через Dokploy.

Настройки приложений и контейнеров меняются через Dokploy API, чтобы
карточки панели оставались источником конфигурации. Проверка CMS:
`/api/health` и `/api/ready`; проверка сайта — те же адреса. У сайта
`commit` находится в health, а readiness подтверждает связь с CMS и
возвращает тот же `buildId`.

Данные старого сервера и загруженные там файлы автоматически не появляются
из Git. Первичное заполнение новой базы из исходников является отдельной
операцией и не заменяет восстановление старой production-базы.

# «Планировка под вас» — локальное ревью, 29 октября 2026

## Статус

Реализован локальный интерактивный прототип внутри существующего `ProjectPlans`. На production ничего не публиковалось. Прототип сохранён в отдельной ветке `codex/plan-request-brief`, основанной на `396f3fb`; main не изменён.

Проверка: http://localhost:3000/catalog/barnhouse-115 — блок «КАК ОН УСТРОЕН ВНУТРИ», кнопка «Предложить свою планировку».

Для двухэтажной планировки: http://localhost:3000/catalog/barnhouse-138.

## Реализовано

- Три самостоятельных сценария: изменение текущей планировки, собственные требования, эскиз.
- Общие контакты с существующей маской и валидацией имени/телефона, выбором предпочтительного канала и обязательным согласием.
- Возврат между этапами и сценариями, сохранение черновика при Escape/закрытии/повторном открытии. Черновик только в памяти вкладки, без localStorage и серверного хранения.
- Идентификатор, код и название проекта, текущие вариант и этаж фиксируются при первом открытии брифа. Новый бриф после завершения получает актуальный контекст проекта.
- Необязательные параметры дома, свой диапазон площади, дополнительные помещения, раскрываемая детализация с добавлением/удалением строк и собственным названием помещения.
- Жилые/вспомогательные помещения внутри тёплого контура, инженерные помещения и терраса представлены отдельными категориями. Автоматического суммирования площадей нет.
- Локальный выбор и drag-and-drop JPG/JPEG, PNG, WebP, PDF до 10 МБ. Проверяются расширение, MIME, размер и сигнатура содержимого. Картинка получает локальный предпросмотр, PDF — карточку файла. Есть удаление и замена; Object URL освобождаются.
- Для сценария эскиза достаточно файла, безопасной HTTP(S)-ссылки или описания. Все поля остальных пожеланий необязательны.
- Zod собирает версионированный типизированный объект с discriminated union, не смешивая поля сценариев.
- Локальный адаптер проверяет объект, показывает состояние обработки и честный результат: «Демонстрация: данные успешно проверены. Заявка никуда не отправлена».

## Desktop и mobile

Исходная структура планировки, переключатели, экспликация и полноэкранный просмотр сохранены. Планировка, экспликация и CTA объединены общей белой поверхностью с одним контуром. На desktop CTA расположен под экспликацией, без отдельной карточки/рамки. Чертёж занимает высоту общей области, пропорции основных колонок сохранены.

На mobile CTA — sticky-элемент CSS-сетки, охватывающий область планировки и экспликации. Он ограничен секцией и исчезает после неё. В конце списка зарезервировано место: последнюю строку можно прочитать полностью. Отступ учитывает safe-area и высоту пересекающегося cookie-уведомления. Глобального fixed-CTA нет.

На mobile диалог — оверлей строго по ширине `.section__inner`, с боковыми отступами контейнера, вертикальными отступами и safe-area; полноэкранный вариант убран. На desktop окно центрируется и имеет фиксированную для всех этапов высоту 640 px, ограниченную доступной высотой экрана. На mobile размер также не меняется между этапами. Внутри независимо прокручивается содержимое; заголовок и панель действий доступны отдельно. `visualViewport` учитывает изменение доступной высоты при клавиатуре. При открытии и переходе этапов поля не получают фокус автоматически.

Используется существующая Radix/shadcn-композиция Dialog и Select. Поддержаны Escape, focus trap, возврат фокуса к CTA, блокировка фоновой прокрутки, уменьшенное движение, связанные сообщения об ошибках. Случайное нажатие на фон не закрывает бриф, явное закрытие сохраняет черновик.

## Локальная конфигурация

В игнорируемом `.env.local` включены:

```dotenv
NEXT_PUBLIC_PLAN_REQUEST_DEMO=1
PLAN_REQUEST_DEMO_FIXTURES=1
```

Первый флаг разрешает прототип только при `NODE_ENV=development`. Даже оба включённых флага не включают его при production-сборке/запуске. Это отдельно проверено модульным тестом.

Второй флаг использует существующие данные из `src/lib/catalog/projects.ts`: локальная CMS в текущем окружении отвечает 500 на чтение каталога. В фикстурах могут быть старые названия и цены — это не актуальный production-каталог. Чтобы использовать локальную CMS после восстановления её данных, установите `PLAN_REQUEST_DEMO_FIXTURES=0`. Production-ветки чтения данных не заменены.

## Ограничения и следующий этап

Это локальный прототип, не рабочий канал приёма заявок. Заявки и файлы не отправляются и не сохраняются в CRM/CMS. Не вызываются реальные цели аналитики. После ухода со страницы или перезагрузки черновик исчезает.

Для реальной интеграции после ревью потребуются согласованный серверный адаптер, защищённая загрузка/хранение файлов, серверная валидация и ограничения частоты, антиспам, идемпотентность и подтверждение доставки, маппинг полей CRM, политика доступа/срока хранения файлов и только затем события успешной заявки.

Поведение проверено в Chromium/WebKit и при изменении viewport; физический iPhone, системная клавиатура и аппаратные вырезы не проверялись. Проверка на реальном устройстве остаётся отдельным этапом. Производственные LCP/TTFB не измерялись: dev-сборка и неисправная локальная CMS не подходят для подтверждения production-бюджетов производительности.

# Релиз CMS

Push в `main` с изменениями `cms/**` или `src/lib/**` запускает workflow
**CMS release**. Он проверяет типы, тесты и схему на пустой базе, затем
публикует `ghcr.io/nikita-yakuschenko/avgst-cms@sha256:…`.

Сайт `new.avgst.ru` этот workflow не собирает и не перезапускает.

Переменная `CMS_RELEASE_ENABLED` сейчас не включается. Пока её нет,
production не мигрируется и не переключается.

## Кто выполняет релиз

GitHub-hosted runner не видит production PostgreSQL и не получает секреты
базы. На сервере Dokploy стоит отдельный runner пользователя `avgst-runner`.
Этот пользователь не входит в группу `docker` и не читает `/etc/avgst`.

Единственная команда, которую ему разрешает sudo:

```
/usr/local/sbin/avgst-cms-release <образ@sha256:…> <SHA>
```

Скрипт принадлежит root, ставится один раз из `cms/host/avgst-cms-release`
и не берётся из checkout. Workflow не клонирует репозиторий на этом runner
и не передаёт `GITHUB_TOKEN`. Job `release` имеет `permissions: contents: none`.

Скрипт принимает только образ
`ghcr.io/nikita-yakuschenko/avgst-cms@sha256:…` с метками этого репозитория
и того же SHA. Контейнер миграции не получает Docker-сокет, ключ Dokploy и
сеть хоста: только сеть базы, `--cap-drop ALL` и корневая файловая система
только для чтения.

Секреты лежат в `/etc/avgst/*.env`, владелец root, права `600`.

Защита `main`: обязательный pull request, запрет force-push, required check
`verify` и review владельца для `.github/workflows/` и `cms/host/`
(`CODEOWNERS`). Runner привязан только к репозиторию `nikita-yakuschenko/site`.

## Один источник конфигурации сервиса

Dokploy записывает полную спецификацию Swarm из карточки приложения:
образ, команда, тома, сеть, healthcheck и политика обновления. Прямой
`docker service update` это состояние расщепляет, поэтому релиз его не
вызывает.

Перед записью скрипт сравнивает digest образа в Dokploy и ID запущенного
контейнера. Если они различаются или в карточке осталась команда, релиз
останавливается и ничего не меняет. Дальше он записывает новый digest и
пустую команду, вызывает только `application.deploy` и ждёт, пока
запущенный контейнер и карточка Dokploy показывают один и тот же образ.
Если этого не произошло, в карточку возвращается предыдущий образ и снова
вызывается Deploy. Схема базы при этом не откатывается.

## Откат образа

Автоматически допускаются только миграции, после которых предыдущий процесс
CMS продолжает читать и писать старые колонки:

- новый enum;
- новая колонка, nullable либо с `DEFAULT`, без `NOT NULL` без значения по умолчанию;
- внешний ключ только на колонку, добавленную в этой же миграции;
- обычный индекс;
- `UPDATE` только этой новой колонки и только `WHERE … IS NULL`.

Не проходят автоматически: `NOT NULL` без `DEFAULT`, ключ или ограничение на
старую колонку, смена типа, `SET DEFAULT` у существующей колонки, уникальный
индекс, новая таблица, удаление и перезапись старых данных. Такая миграция
останавливает pipeline до резервной копии.

`/api/health` без совпавшей ревизии и `/api/ready` без полного списка
миграций успехом не считаются.

## Однократный bootstrap

Обычный релиз не удаляет `batch = -1`. Отдельный скрипт
`cms/host/avgst-cms-bootstrap` сначала только печатает историю
`payload_migrations` и наличие колонок из ещё не применённых миграций.
`--apply` удаляет ровно одну запись `dev` с `batch = -1`, если других
аномалий нет, и не запускает миграции. GitHub Actions этот скрипт не
вызывает.

Порядок включения описан в конце файла и выполняется только после проверки
образа. `CMS_RELEASE_ENABLED` до этого не создавать.
